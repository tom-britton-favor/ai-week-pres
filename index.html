Something is wrong with a menu.

  • Data lives across 4+ services: merchant, location, menu, hydration
  • Complex state: feature flags, cache versions, permissions, validation errors
  • Tracking it down = many API calls, lots of context-switching
- Classic support scenario: message from content team message, menu looks wrong
- To diagnose you need merchant status, location config, menu validation, cache state, feature flags — a combination of API calls and digging through FPP.
- Requires deep domain knowledge just to know where to look

Stage 1

The CLI

Why CLI?

  • AI agents excel at driving CLIs
  • Less complexity than MCP
  • SKILL.md runbook embedded in the binary

Why not Postman / raw API?

  • Output formatted for humans
    (AGENT CONTEXT blocks)
  • Saves tokens vs raw JSON
- AI agents are great at reading help text and chaining commands — CLIs play to that strength
- MCP requires a running server and more infrastructure; CLI is just a binary
- SKILL.md is a diagnostic runbook — tells Claude exactly how to use the tool and what to look for
- Raw API responses are noisy; fvr strips and formats data so Claude spends tokens on reasoning, not parsing

Stage 1

CLI Capabilities


fvr auth                # login / logout
fvr merchant            # get, search, locations, accounts
fvr location            # get, debug
fvr menu                # get, list, validate, version, cache-status, cache-clear
fvr plugin install      # registers SKILL.md with Claude Code
- Written in Go — single binary, no install dependencies for users
- Covers the full diagnostic surface: merchant → location → menu → cache
- `location debug` runs a set of P4 diagnostic checks
- `menu validate` calls the validation service directly
- `plugin install` is what wires it into Claude Code

Stage 2

The Claude Plugin

fvr plugin install → SKILL.md registered with Claude Code


# Ask Claude Code:
"Why is the Happy Chicks menu showing the wrong items?"

# Claude autonomously drives:
fvr merchant search "Happy Chicks"        # → retailer UUID
fvr merchant locations <retailer-uuid>    # → location list + legacy IDs
fvr menu validate <legacy-id>            # → validation errors
fvr menu cache-status <legacy-id>        # → stale cache detected

Produces a full diagnostic report with root cause & next steps.

- One install command, then just talk to Claude normally
- Claude reads the SKILL.md runbook and knows exactly what commands to run in what order
- Handles ID translation automatically — UUIDs vs legacy IDs, Claude figures it out
- The final report is surprisingly good: root cause, affected entities, recommended action
- What used to take 20 minutes of manual API calls takes about 30 seconds

Building Methodology

Have used a heavy spec-driven workflow in the past resulting in great tedium and poor results. Decided to try a just-in-time planning approach for this project. Good results.

  1. Brainstorm in web chat — Opus model
  2. Export PRD → docs/ directory
  3. Claude Code reads PRD → plan.md with checkboxes
  4. Per epic: refine → story markdown files
  5. Per story: Plan mode → implementation plan first
  6. Implement with manual confirmation of every edit using TDD methodology
  7. Code review agent after each story
  8. Fix → commit → next story

Coverage: 78.9% overall  ·  core packages: 95–100%

- Previous experience with BMAD: too much upfront design, felt like writing documentation for documentation
- JIT approach: plan just enough to start, then let the work inform the next step
- Confirming every edit kept me in the loop — AI didn't go rogue, I understood all the code
- TDD + code review agent after each story caught issues early, kept quality high
- Coverage numbers reflect that discipline — not an afterthought

Why Go?

  • Simple language — less surface area for AI to get wrong
  • No runtime needed — no Node.js, Python, or Java to install
  • Compiles to a single binary — trivial distribution
  • Static asset embedding — SKILL.md lives inside the binary
  • Explicit error handling
- Go's simplicity matters for AI-assisted development — fewer footguns, less ambiguity
- Distribution was a real concern: `go install` or just copy the binary, nothing else needed
- Embedding SKILL.md means the runbook ships with the tool automatically — no separate install step
- Explicit errors made it easy to spot mistakes during code review
